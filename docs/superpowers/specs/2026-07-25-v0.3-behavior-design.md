# EyeSee v0.3 — Behavior — Design

Date: 2026-07-25

## Purpose

Turn the v0.2 "eyes that move correctly when told to" firmware into "eyes
that act on their own." Per `docs/ROADMAP.md`'s v0.3 milestone:

- `EyeState`-driven behavior switching in `BehaviorEngine`
- `TrackingBehavior`, `CuriousBehavior`, `RandomBehavior`, `SleepBehavior`
- Idle scanning / micro-saccades
- Animated blink (close + reopen), expression pose blending

No new hardware/networking surface this pass — everything here is pure
logic sitting between `CommandQueue`/`BehaviorEngine` and `IAnimationEngine`,
fully native-testable.

## EyeState-driven behavior switching

`BehaviorEngine` currently holds exactly one hardcoded `IBehavior`
(`IdleBehaviorStub`), injected via constructor, ignoring `EyeState`
entirely. This pass adds a registration API and a lookup table:

```cpp
class BehaviorEngine : public IBehaviorEngine {
public:
    BehaviorEngine(IAnimationEngine& animation, CommandQueue& commandQueue, IBehavior& fallbackBehavior);

    /** Associates a behavior instance with a state. Called once per behavior during setup(). */
    void registerBehavior(EyeState state, IBehavior& behavior);

    void setState(EyeState state) override;   // now also swaps activeBehavior_, calling onExit/onEnter
    EyeState state() const override;
    void update(uint32_t deltaMs) override;
    // dispatch() unchanged

private:
    IBehavior& fallbackBehavior_;
    std::array<IBehavior*, /* one slot per EyeState value */> behaviorsByState_{};
    IBehavior* activeBehavior_;
    EyeState state_ = EyeState::Startup;
};
```

`registerBehavior(state, behavior)` stores `&behavior` at
`behaviorsByState_[static_cast<size_t>(state)]` — a fixed-size
`std::array`, no dynamic allocation, sized to `EyeState`'s 8 values.
`setState(state)` looks up the registered behavior for that state
(falling back to `fallbackBehavior_` if none was registered for it), calls
the outgoing behavior's `onExit()`, swaps `activeBehavior_`, then calls the
incoming behavior's `onEnter(animation_)`.

`IBehavior` gains an `onEnter`/`onExit` lifecycle pair, both with a default
no-op body (not pure virtual — most behaviors don't need them; only
`SleepBehavior` genuinely does):

```cpp
class IBehavior {
public:
    virtual ~IBehavior() = default;
    virtual void onEnter(IAnimationEngine& animation) {}
    virtual void onExit(IAnimationEngine& animation) {}
    virtual void update(uint32_t deltaMs, IAnimationEngine& animation) = 0;
    virtual EyeState state() const = 0;
};
```

Since `update()` is only ever called on the currently-active behavior, an
inactive behavior's internal timers (e.g. "time until next glance")
correctly stay paused while inactive — no extra reset-on-enter logic is
needed for that. `onEnter`/`onExit` exist specifically for behaviors that
need a one-time *action* on transition (only `SleepBehavior`, this pass).

## Random glances (`IRandomSource`)

`IdleBehavior`, `CuriousBehavior`, and `RandomBehavior` all need randomness
for "glance somewhere plausible after some interval." A shared, injectable
interface keeps them native-testable with deterministic sequences:

```cpp
class IRandomSource {
public:
    virtual ~IRandomSource() = default;
    virtual float nextFloat(float min, float max) = 0;
    virtual uint32_t nextUInt(uint32_t min, uint32_t max) = 0;
};
```

`ArduinoRandomSource` (esp32dev-only, wraps Arduino's `random()`) is the
real implementation; `FakeRandomSource` (test double, returns a
pre-programmed sequence) is used in native tests, following the same
pattern as `FakeServoOutput`/`FakeAnimationEngine`.

## The four behaviors

All four implement `IBehavior`, are constructed with an `IRandomSource&`
(except `SleepBehavior`, which needs none), and are registered by
`main.cpp` against one `EyeState` each.

**`IdleBehavior`** (`EyeState::Idle`) — replaces `IdleBehaviorStub`. On each
`update()`, decrements an internal countdown; when it hits zero, issues one
small random gaze `animateGaze()` call (a "micro-saccade": a small offset
within a tight range, e.g. ±0.15 normalized) and resets the countdown to a
new random interval (e.g. 500-2000ms). This is idle scanning + micro-saccades
in one behavior, since they're the same mechanism at different amplitudes/frequencies for this pass — no need for two separate behaviors to satisfy one roadmap bullet.

**`TrackingBehavior`** (`EyeState::Tracking`) — holds a settable target
(`setTrackedTarget(float x, float y)`, called by future input sources; v0.3
has no live camera/sensor feeding it, that's v0.6's face-tracking bridge).
On `update()`, issues one `animateGaze()` call whenever the tracked target
changes (a dirty-flag guard prevents redundant calls that would otherwise
restart the eased transition from scratch every frame), at a fixed, faster
speed than idle glances (a real, testable "track this point" behavior —
just with no live input source wired up yet, exactly like `RestApi`'s
routes are real-shaped but unimplemented in v0.1).

**`CuriousBehavior`** (`EyeState::Manual` is already used for direct
control, so `CuriousBehavior` piggybacks on... actually `EyeState` has no
dedicated `Curious` value. `CuriousBehavior` and `RandomBehavior` are
registered under `EyeState::Idle` alongside `IdleBehavior`? No — only one
behavior can be registered per state. Resolution below.)

### Resolving `EyeState` vs. behavior-count mismatch

`EyeState` has 8 values (`Startup, Calibration, Manual, Idle, Tracking,
Sleeping, Disabled, Error`) but the roadmap names *four* behaviors
(`Tracking`, `Curious`, `Random`, `Sleep`) plus idle scanning — five
behavior concepts for states that don't 1:1 cover them. Rather than adding
new `EyeState` values (a bigger, cross-cutting change touching
`EyeCommand`/tests/docs for a v0.3 behavior detail), `CuriousBehavior` and
`RandomBehavior` are both registered under `EyeState::Idle`, but only one
is *the* registered idle behavior at a time — this pass, `IdleBehavior`
is what's wired into `main.cpp` for `EyeState::Idle`, and `CuriousBehavior`/
`RandomBehavior` are built, tested, and documented as available
alternatives (a future config or REST endpoint, v0.4+, can swap which one
`main.cpp` registers for `Idle`). This keeps `EyeState` stable and treats
"which idle personality is active" as a wiring choice, not a state-machine
concept — consistent with `IBehavior` already being designed as a
pluggable strategy.

**`SleepBehavior`** (`EyeState::Sleeping`) — `onEnter()` calls
`animation.animateSleep(500)` once; `update()` is a no-op (eyes just stay
shut). `onExit()` is a no-op too — the behavior itself never decides to
wake up (see below).

### `Sleep`/`Wake` commands also drive the state transition

`BehaviorEngine::dispatch()` gets one small addition: after routing a
`CommandType::Sleep` to `animation_.animateSleep()`, it also calls
`setState(EyeState::Sleeping)`; after routing `CommandType::Wake` to
`animation_.animateWake()`, it also calls `setState(EyeState::Idle)`. This
is centralized in `BehaviorEngine` (the natural owner of state
transitions) rather than left for a future REST layer to remember to do —
a client that sends `Wake` gets both the eyes reopening *and* idle
scanning resuming, which is the only sensible combined effect. No other
`CommandType` triggers a state transition (`Blink`/`WinkLeft`/`WinkRight`/
`Look`/`SetExpression` are momentary actions, not state changes).

## Animated blink (close + reopen)

`RealAnimationEngine::animateBlink()` currently only closes and never
reopens (the v0.2-documented limitation). `EyelidTransition` gains one
field:

```cpp
bool autoReopenOnComplete = false;
```

When an eyelid transition completes and `autoReopenOnComplete` is `true`,
`update()` clears the flag (preventing infinite reopen-loops) and
immediately starts a new eyelid transition targeting fully open
(`1,1,1,1`) using the *same duration* the close phase used — a symmetric
close/open blink. `animateBlink(durationMs)` sets the flag after starting
the close transition; `winkLeft`/`winkRight`/`sleep` never set it (they
remain one-way, matching their existing documented semantics — only
*blink* auto-reopens). A full `animateBlink(150)` call therefore takes
~300ms total (150ms close + 150ms reopen).

## Expression pose blending

A single source of truth for "what does each `Expression` numerically
mean," shared by both the instant (`EyeController::setExpression`) and
animated (`RealAnimationEngine::animateExpression`) paths:

```cpp
// lib/EyeController/ExpressionPose.h
struct ExpressionEyelidTarget {
    float upperLid;
    float lowerLid;  // same value applied to both left/right pairs — expressions are symmetric this pass
};

ExpressionEyelidTarget expressionEyelidTarget(Expression expression);
```

Expressions only affect eyelid aperture, not gaze — an expression applied
mid-saccade doesn't interrupt where the eyes are looking. Values (a
deliberately simple, documented design choice — not claimed to be
anatomically precise):

| Expression | upperLid | lowerLid |
|---|---|---|
| Neutral | 0.85 | 0.85 |
| Happy | 0.5 | 0.7 |
| Curious | 1.0 | 0.9 |
| Sleepy | 0.3 | 0.5 |
| Angry | 0.6 | 0.9 |
| Surprised | 1.0 | 1.0 |

`EyeController::setExpression()` now looks up this table and applies the
resulting pose instantly (preserving current gaze) — still consistent with
invariant 1 (no timed state in `EyeController`). `RealAnimationEngine::animateExpression(expression, durationMs)` looks up the *same* table and
starts an eyelid transition toward it (EaseInOut easing, matching every
other eyelid move) instead of calling `setExpression()` directly — this is
what makes it a real *blend* rather than an instant snap.

## Out of Scope (deferred, not v0.3)

- Real face-tracking, MQTT, or Bluetooth gamepad input (v0.6) —
  `TrackingBehavior`'s target is settable via a plain method call this
  pass; nothing feeds it live sensor data yet.
- Per-eye asymmetric expressions (e.g. a wink-like one-sided smirk) —
  expressions stay symmetric left/right.
- Configurable/swappable idle personality via REST or persisted config
  (v0.4+) — `main.cpp` hardcodes which behavior is registered for
  `EyeState::Idle`.
- New `EyeState` values for `Curious`/`Random` — resolved by registering
  multiple concrete behaviors as available-but-not-all-simultaneously-
  active implementations, not by growing the state enum.

## Testing

All new logic is native-testable: `IRandomSource`/`FakeRandomSource` make
the four behaviors deterministic in tests; `BehaviorEngine`'s registration
table, `RealAnimationEngine`'s reopen sequencing, and
`expressionEyelidTarget()`'s lookup table are all plain logic with no
Arduino dependency.
