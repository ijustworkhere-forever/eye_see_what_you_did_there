# EyeSee v0.6 — Integrations — Design

Date: 2026-07-26

## Purpose

Give the eyes three new ways to be driven, per `docs/ROADMAP.md`'s v0.6
milestone:

- Face-tracking bridge
- MQTT
- Bluetooth gamepad control

All three are new *input sources* into the exact same pipeline every prior
milestone built toward: they each end up pushing an `EyeCommand` into the
shared `CommandQueue`, arbitrated by `BehaviorEngine`, same as the REST API,
WebSocket, and Web UI already do. No new pipeline stage, no new way for an
input source to reach `EyeController`/hardware directly.

## Module organization: a new `lib/Integrations`

MQTT and Bluetooth gamepad are genuinely new *external protocol*
integrations (this milestone's own name), distinct from `lib/Networking`
(HTTP/WebSocket-specific) — they get a new leaf library, `lib/Integrations`,
holding `MqttBridge` and `GamepadBridge` (Arduino-bound) plus
`GamepadInputMapper` (pure, native-tested). Face-tracking is *not* a new
external-protocol integration — it reuses the REST API's existing JSON/
route machinery and extends `Behavior`'s existing `TrackingBehavior`
(built in v0.3, never fed real input), so it lives in `lib/Networking` +
`lib/Behavior` + `lib/Protocol`, not `lib/Integrations`.

## Face-tracking bridge

### The missing piece: `GazeTarget.hold`

`GazeTarget.hold` has existed since v0.2, unused — the original v0.2 spec
scoped it as "a future signal for behavior logic... deciding whether to
auto-return to center," explicitly not something the animation engine
itself should act on. `TrackingBehavior` (v0.3) already sets `hold = true`
unconditionally on every `animateGaze()` call it issues — meaning
"continue holding the last position, never auto-recenter" has been the
*only* behavior available, by omission (nothing ever built the
auto-recenter path). This milestone finally builds the other half: a
staleness timeout, so losing a tracked face can either keep holding (as
today) or recenter, per-request.

### New command type: `CommandType::Track`

Face-tracking data doesn't fit `CommandType::Look` — `Look` is dispatched
straight to `IAnimationEngine::animateGaze()` regardless of the active
`EyeState`/behavior (a one-shot manual command), while tracking needs to
(a) put the system into `EyeState::Tracking` and (b) feed the *active*
behavior a continuous stream of targets. `EyeCommand`/`CommandType` gains:

```cpp
enum class CommandType {
    Look,
    Blink,
    WinkLeft,
    WinkRight,
    Sleep,
    Wake,
    SetExpression,
    Track  // new
};
```

`Track` commands carry the same `gazeTarget` field `Look` already uses
(no new `EyeCommand` field needed) — `x`/`y`/`hold` are populated;
`speed`/`blinkOnArrival` are ignored for `Track` (tracking always moves at
`TrackingBehavior`'s own fixed `kTrackingSpeedDegPerSec`, matching its
existing v0.3 design).

### `IBehavior` gains an optional hook

`BehaviorEngine::dispatch()` doesn't have direct access to any specific
concrete `IBehavior` (only the generic registration table) — so routing a
`Track` command's payload to `TrackingBehavior` needs a new, generically-
dispatchable method on the interface, default no-op (matching
`onEnter`/`onExit`'s existing pattern — most behaviors don't need it):

```cpp
class IBehavior {
public:
    // ... existing onEnter/onExit/update/state unchanged ...

    /** Delivers a Track command's payload to whichever behavior is currently
     * active. Default no-op -- only TrackingBehavior overrides this. */
    virtual void receiveGazeTarget(const GazeTarget& target) {
        (void)target;
    }
};
```

`BehaviorEngine::dispatch()` gains one case:

```cpp
case CommandType::Track:
    setState(EyeState::Tracking);
    activeBehavior_->receiveGazeTarget(command.gazeTarget);
    break;
```

(`setState()` runs first so that if this is the *first* `Track` command
after some other state, `TrackingBehavior::onEnter()` fires before
`receiveGazeTarget()` — consistent with every other state-transition-plus-
payload command in this codebase, e.g. `Sleep`'s `setState`-then-animate
ordering from v0.3.)

### `TrackingBehavior` redesign: staleness timeout

```cpp
class TrackingBehavior : public IBehavior {
public:
    void receiveGazeTarget(const GazeTarget& target) override;  // replaces setTrackedTarget(x, y)

    void update(uint32_t deltaMs, IAnimationEngine& animation) override;
    EyeState state() const override;

private:
    static constexpr float kTrackingSpeedDegPerSec = 500.0f;
    static constexpr uint32_t kStaleTimeoutMs = 3000;  // no update in 3s -> face considered lost

    GazeTarget lastTarget_{};
    bool targetChanged_ = false;
    bool hasTarget_ = false;
    bool recentered_ = false;
    uint32_t msSinceLastUpdate_ = 0;
};
```

`receiveGazeTarget(target)`: stores `lastTarget_ = target` (so its `hold`
flag travels with it), sets `targetChanged_ = true`, resets
`msSinceLastUpdate_ = 0`, sets `hasTarget_ = true`, clears `recentered_`.

`update(deltaMs, animation)`:
1. If `targetChanged_`: issue `animateGaze()` toward `lastTarget_` at
   `kTrackingSpeedDegPerSec` (the existing v0.3 dirty-flag-guarded logic,
   unchanged in spirit), clear `targetChanged_`.
2. Else if `hasTarget_` and not `recentered_`: accumulate
   `msSinceLastUpdate_ += deltaMs`; once it reaches `kStaleTimeoutMs`:
   - if `lastTarget_.hold` is `false`: issue one `animateGaze()` back to
     center (`{x: 0, y: 0}`, same speed) and set `recentered_ = true` (so
     this fires exactly once, not every frame past the timeout).
   - if `lastTarget_.hold` is `true`: do nothing — hold indefinitely,
     matching today's only-available behavior.
3. A new `receiveGazeTarget()` call at any point (even after recentering)
   resumes tracking normally — `recentered_` and the timeout reset
   together in step 1's trigger path.

This stays entirely inside `TrackingBehavior` — no behavior-initiated
`EyeState` transition is needed (a real architectural constraint: no
`IBehavior` can call `BehaviorEngine::setState()` today, and adding that
capability is a bigger change than this milestone needs). Recentering is a
*visual* action, not a state change; the system stays in
`EyeState::Tracking` until a different command (e.g. `Sleep`, or a
`Look`/`Blink` from another input source) moves it elsewhere.

### New REST route: `POST /api/v1/track`

```
POST /api/v1/track
{"x": float, "y": float, "hold"?: bool}   -- x/y required, clamped to [-1, 1]; hold defaults to true
```

A new `lib/Protocol/EyeCommandJson` function, `parseTrackCommand`, mirrors
`parseLookCommand`'s x/y-required-and-clamped shape exactly, but defaults
`hold` to `true` (not `false`, unlike `Look`) — tracking's whole point is
holding position between detections, so silently losing the face on a
missed update (the common case with any real face-tracking client) should
default to *not* recentering, unless a client explicitly opts out via
`"hold": false`. Sets `out.type = CommandType::Track`.

The design deliberately does *not* invent a new external protocol for
face-tracking — it's designed so an external face-tracking client (e.g. a
Python script on a PC running OpenCV/MediaPipe over a webcam) is just
another REST client, `POST`ing to `/api/v1/track` at whatever cadence its
face-detection loop runs, exactly like the Web UI already `POST`s to
`/api/v1/look`.

## MQTT

### Why MQTT reuses `lib/Protocol`'s JSON logic, not new parsing

MQTT messages carry the same command vocabulary the REST API already
has — the only difference is *transport* (pub/sub over a persistent TCP
connection to a broker, not per-request HTTP) and that a single
subscribed topic must disambiguate which command a payload represents
(a REST route's path already does this; MQTT needs an explicit field).
One new `lib/Protocol` function, `parseMqttCommand`, reads a `"type"`
field and dispatches to the existing per-type parse functions:

```cpp
// lib/Protocol/MqttCommandJson.h
struct MqttParseResult {
    bool ok = false;
    std::string error;
    EyeCommand command;
};

/** Reads body["type"] ("look"|"blink"|"wink"|"expression"|"sleep"|"wake"|"track")
 * and dispatches to the matching lib/Protocol parse function. */
MqttParseResult parseMqttCommand(JsonVariantConst body);
```

This is the one new piece of native-testable logic MQTT needs — everything
else (the six existing `parse*Command` functions, `buildStatusJson`) is
already built and already tested.

### `lib/Integrations/MqttBridge`

```cpp
class MqttBridge {
public:
    MqttBridge(CommandQueue& commandQueue, const IBehaviorEngine& behaviorEngine,
               const EyeController& eyeController, const WifiManager& wifiManager);

    /** Configures the client and attempts an initial connection. Call once from
     * setup(), any time after WifiManager::begin(). */
    void begin(const char* brokerHost, uint16_t brokerPort, const char* topicPrefix);
    /** Services the MQTT connection: reconnects with backoff if dropped, pumps
     * incoming messages, and periodically publishes a status update. */
    void update(uint32_t deltaMs);

private:
    static constexpr uint32_t kReconnectIntervalMs = 5000;   // matches WifiManager's retry cadence
    static constexpr uint32_t kStatusPublishPeriodMs = 1000; // 1Hz -- status changes far slower than the 30Hz WS broadcast
};
```

Subscribes to `<topicPrefix>/command` (default prefix `eyesee`, so
`eyesee/command`); publishes to `<topicPrefix>/status` at 1Hz using the
existing `buildStatusJson()`. `PubSubClient::setCallback()`'s signature is
conditional on target platform — verified against the installed package's
header: on `ESP32`/`ESP8266` specifically it's
`std::function<void(char*, uint8_t*, unsigned int)>` (not a plain C
function pointer, which is the fallback for other platforms), so `begin()`
can register a capturing lambda directly (`[this](char* topic, uint8_t*
payload, unsigned int length) { ... }`) with no static-instance-pointer
workaround needed.

On a received message: parse via `parseMqttCommand`; on success, push the
resulting `EyeCommand` into the shared `CommandQueue` (503-equivalent
behavior on a full queue is a debug log, not an MQTT response — MQTT
pub/sub has no request/response semantics to return an error through,
unlike REST's 4xx/5xx). On failure, log the parse error via `Logger`.

### Credentials: `include/MqttCredentials.h`, same pattern as WiFi

```cpp
// include/MqttCredentials.h.example
#pragma once
constexpr const char* kMqttBrokerHost = "192.168.1.100";
constexpr uint16_t kMqttBrokerPort = 1883;
constexpr const char* kMqttTopicPrefix = "eyesee";
```

Gitignored real file, committed `.example` template, CI gets a placeholder
copy before the build step — identical mechanism to v0.4's
`WifiCredentials.h`, extended (not replaced) in `.gitignore`/
`ci.yml`.

## Bluetooth gamepad control

### Library choice: `tbekas/BLE-Gamepad-Client`, not Bluepad32

The obvious-sounding choice, Bluepad32, requires swapping this project's
Arduino framework for a custom `bluepad32-arduino` PlatformIO framework —
a much bigger, riskier change than adding a library, and one that could
jeopardize compatibility with ESPAsyncWebServer/ArduinoOTA/Adafruit's PWM
driver, all already depended on. `tbekas/BLE-Gamepad-Client` (verified
against the actual installed package: `Compatible Platforms: espressif32`,
`Compatible Frameworks: arduino` — the exact same platform/framework this
project already targets) is a normal library, built on `h2zero/NimBLE-Arduino`,
supporting the Xbox Wireless Controller and Steam Controller as a BLE HID
*host* (the ESP32 connects *to* the gamepad, not the reverse). Its actual
API (verified against the installed package's headers/examples):

```cpp
XboxController controller;
controller.begin();
controller.onValueChanged([](XboxControlsState& s) { /* s.leftStickX, s.buttonA, ... */ });
controller.onConnected(...); controller.onDisconnected(...);
```

`XboxControlsState` exposes `leftStickX/Y`/`rightStickX/Y` (floats, -1..1),
`buttonA/B/X/Y`, `leftBumper`/`rightBumper`, `dpadUp/Down/Left/Right`,
`leftStickButton`/`rightStickButton`, `leftTrigger`/`rightTrigger`
(floats, 0..1), and several menu-style buttons.

### `lib/Integrations/GamepadInputMapper` (pure, native-tested)

A library-agnostic input struct decouples the pure mapping logic from
`BLE-Gamepad-Client`'s concrete `XboxControlsState` type, so this file has
zero BLE/Arduino dependency:

```cpp
// lib/Integrations/GamepadInputMapper.h
struct GamepadState {
    float leftStickX = 0.0f;
    float leftStickY = 0.0f;
    bool buttonA = false;
    bool buttonB = false;
    bool buttonX = false;
    bool buttonY = false;
    bool leftBumper = false;
    bool rightBumper = false;
};

/** Maps one frame of gamepad state to zero or more EyeCommands, given the
 * previous frame's state (for edge-detecting button presses -- a held button
 * must fire its action once, not every frame). Writes into outCommands (fixed
 * capacity, no heap allocation -- matches CommandQueue's own discipline) and
 * returns the count actually written; at most kMaxCommandsPerFrame (one Look
 * from the stick + one per the six mapped buttons = 7). */
constexpr size_t kMaxCommandsPerFrame = 7;

size_t mapGamepadState(const GamepadState& current, const GamepadState& previous,
                        std::array<EyeCommand, kMaxCommandsPerFrame>& outCommands);
```

Mapping (a deliberately simple, documented, easily-remapped choice — not
claimed to be the only sensible one):
- Left stick (`leftStickX`/`leftStickY`) → `CommandType::Look` every frame
  the stick is off-center beyond a small deadzone (`0.1`, avoiding stick-
  drift jitter), `x`/`y` passed straight through (already -1..1, matching
  `GazeTarget`'s range) — centered stick emits nothing (not a `Look{0,0}`
  every frame; the eyes simply stay where they last were, exactly like the
  Web UI joystick's release behavior).
- `buttonA` (press edge) → `CommandType::Blink`.
- `leftBumper` (press edge) → `CommandType::WinkLeft`.
- `rightBumper` (press edge) → `CommandType::WinkRight`.
- `buttonY` (press edge) → `CommandType::SetExpression(Happy)`.
- `buttonB` (press edge) → `CommandType::Sleep`.
- `buttonX` (press edge) → `CommandType::Wake`.

"Press edge" means `current.button == true && previous.button == false` —
every button-triggered command fires exactly once per physical press, not
repeatedly while held.

### `lib/Integrations/GamepadBridge` (Arduino/BLE-bound)

```cpp
class GamepadBridge {
public:
    explicit GamepadBridge(CommandQueue& commandQueue);

    /** Starts BLE scanning/auto-connect for a supported controller. Call once
     * from setup(). */
    void begin();
    /** No-op -- BLE-Gamepad-Client's controller.onValueChanged() callback drives
     * this class, not a polled update(); kept for the shared per-frame update()
     * convention every Networking/Integrations class follows. */
    void update(uint32_t deltaMs);
};
```

`begin()` calls `BLEGamepadClient::init()`, constructs an `XboxController`,
registers `onValueChanged` (translates `XboxControlsState` to this
module's own `GamepadState`, calls `mapGamepadState()`, pushes every
resulting `EyeCommand` into `commandQueue_`) and `onConnected`/
`onDisconnected` (logged via `Logger`, no behavioral effect — losing the
gamepad mid-session isn't an error condition, the eyes just stop receiving
new commands from this source, same as any other input source going
quiet).

### A real, acknowledged risk: flash budget and BLE/WiFi coexistence

`esp32dev`'s flash usage was already at 74.1% before this milestone
(`docs/superpowers/plans/2026-07-26-v0.5-persistence-ota.md`'s Task 6
verification). `NimBLE-Arduino` + `BLE-Gamepad-Client` + `PubSubClient`
are a nontrivial addition. This design does not pre-emptively redesign
the partition table on guesswork — the implementation plan's first task
adds the dependencies and immediately measures real flash usage via
`pio run -e esp32dev`'s own reported percentage, which is authoritative
(not a guess). **If usage approaches or exceeds capacity, the fix is a
custom `partitions.csv`** shrinking the LittleFS partition (the Web UI's
three files are tiny; it doesn't need anywhere near its current default
allocation) to give both OTA app partitions more room — this is called
out explicitly as the contingency, not designed speculatively now.
BLE+WiFi coexistence on ESP32 is a supported, commonly-used combination
in the underlying ESP-IDF/Arduino core (both share one radio via
time-division multiplexing managed by the IDF) — a real concern for
*performance* (BLE scanning can transiently affect WiFi latency) but not
a *correctness* blocker; this is flagged as a manual hardware-validation
item (see Testing) rather than something native tests or a clean compile
can prove either way.

## Out of Scope (deferred, not v0.6)

- Steam Controller support (the library supports it; this design only
  wires up `XboxController` — adding `SteamController` later is a small,
  additive change following the exact same pattern, not attempted now to
  keep this milestone's hardware-validation surface to one controller
  type).
- MQTT TLS/authentication beyond a plain broker connection — matches this
  project's existing LAN-local, no-accounts-model security posture (same
  reasoning as v0.4's REST/WS and v0.5's OTA deferrals).
- A custom `partitions.csv` — only built if the real, measured flash
  usage after adding dependencies actually requires it (see above).
- Any behavior-initiated `EyeState` transition mechanism (`IBehavior`
  calling `BehaviorEngine::setState()` itself) — `TrackingBehavior`'s
  recenter-on-stale-timeout stays a visual action within `Tracking` state,
  not a transition back to `Idle`; building that generic capability is a
  bigger architectural change than this milestone's face-tracking feature
  needs.
- Vibration/force-feedback (the library exposes `XboxVibrationsCommand`)
  — no roadmap driver for it.

## Testing

`lib/Protocol/EyeCommandJson::parseTrackCommand` and
`lib/Protocol/MqttCommandJson::parseMqttCommand` are native-tested exactly
like every other `lib/Protocol` function. `TrackingBehavior`'s staleness-
timeout logic (recenter-on-hold-false, hold-indefinitely-on-hold-true,
resuming on a fresh target) is fully native-testable via the existing
`FakeAnimationEngine` double — no new test infrastructure needed.
`lib/Integrations/GamepadInputMapper` is fully native-tested (deadzone,
press-edge detection for every mapped button, centered-stick-emits-nothing).
`lib/Integrations/MqttBridge`/`GamepadBridge` (Arduino/BLE/MQTT-bound) and
`BehaviorEngine`'s new `Track` dispatch case's integration with a *real*
`TrackingBehavior` instance are verified only by `pio run -e esp32dev`
compiling successfully, matching every other hardware-bound class in this
project — actual MQTT broker connectivity and actual Bluetooth gamepad
pairing/decoding can only be verified on real hardware with a real broker/
controller in hand, which is a manual validation step for whoever next
flashes the device, same as this project's WiFi/OTA/PCA9685 work has
always required.
