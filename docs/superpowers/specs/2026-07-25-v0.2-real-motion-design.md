# EyeSee v0.2 — Real Motion — Design

Date: 2026-07-25

## Purpose

Turn the v0.1 scaffold into eyes that actually move. v0.1 built the full
module tree with every conversion stage present but stubbed: `EyeController`
always reports neutral pulses regardless of pose, `PassthroughAnimationEngine`
applies poses instantly with no timing, and `main.cpp`'s `loop()` runs as
fast as the scheduler allows. v0.2 replaces those three stubs with real
implementations, per `docs/ROADMAP.md`'s v0.2 milestone:

- `EyeController::toServoOutput()` calibration math (scaling, invert, mirror, offset)
- `IAnimationEngine` real interpolation: linear, ease-in/out, cubic
- `GazeTarget.speed`/`.hold` honored (speed fully; hold deferred, see Out of Scope)
- Frame-rate pacing in `loop()` at the documented 100Hz target

**Explicitly not in scope** (see "Out of Scope" below): blink's auto-reopen,
expression pose blending, and anything behavior-level — those are v0.3 per
the already-approved roadmap. v0.2 is motion; v0.3 is behavior.

## Frame pacing

`main.cpp`'s `loop()` gates the update chain on a fixed period instead of
running unconditionally:

```cpp
constexpr uint32_t kFramePeriodMs = 10;  // 100Hz

void loop() {
    const uint32_t nowMillis = millis();
    const uint32_t elapsed = nowMillis - lastFrameMillis;
    if (elapsed < kFramePeriodMs) {
        return;
    }
    lastFrameMillis = nowMillis;

    behaviorEngine.update(elapsed);
    animationEngine.update(elapsed);
    eyeController.update(elapsed);
    servoOutput.update(elapsed);
    // networking/OTA update() calls unchanged
}
```

No drift-correcting accumulator: a simple gate is sufficient here (jitter
of a millisecond or two is imperceptible for a hobbyist eye mechanism), and
it avoids the "spiral of death" risk an accumulator has if any single
frame's work ever exceeds the period. The real elapsed `dt` is still what
gets passed to every `update()`, so animation timing stays accurate
regardless of minor scheduling jitter.

## Calibration math (`EyeController::toServoOutput()`)

Converts an `EyePose` into a `ServoOutput` using each channel's `ServoConfig`
(`minPulseUs`/`maxPulseUs`/`neutralPulseUs`/`mechanicalOffset`/`inverted`/`mirrored`).

**Gaze channels (LR, UD)** — input is `pose.lookX`/`pose.lookY`, normalized -1..1:

```cpp
float effective = input * (config.inverted ? -1.0f : 1.0f) * (config.mirrored ? -1.0f : 1.0f);
float pulse = effective >= 0.0f
    ? config.neutralPulseUs + effective * (config.maxPulseUs - config.neutralPulseUs)
    : config.neutralPulseUs + effective * (config.neutralPulseUs - config.minPulseUs);
pulse = clamp(pulse + config.mechanicalOffset, config.minPulseUs, config.maxPulseUs);
```

Asymmetric scaling toward max vs min since neutral isn't necessarily the
midpoint of the pulse range.

**Eyelid channels (TL, BL, TR, BR)** — input is the corresponding lid field,
0 (closed)..1 (open):

```cpp
float effective = input;
if (config.inverted) effective = 1.0f - effective;
if (config.mirrored) effective = 1.0f - effective;  // same toggle mechanism as inverted — see below
float pulse = clamp(config.minPulseUs + effective * (config.maxPulseUs - config.minPulseUs)
                     + config.mechanicalOffset, config.minPulseUs, config.maxPulseUs);
```

(Applying both flips a second time cancels out — `inverted && mirrored` on
one eyelid channel is equivalent to neither being set. That's the correct
behavior if they're genuinely the same toggle mechanism, per the note
below.)

`inverted` and `mirrored` are treated as two independent, per-channel
sign-flip toggles with the same mechanical effect (different physical
reasons to set them — "this servo horn is mounted backwards" vs "this is
the mirror-image channel of its pair") — not cross-channel logic where one
channel's output depends on another channel's input. Each channel only
ever reads its own `EyePose` field. Both flags are already independently
settable per channel via `CalibrationManager::setServoConfig()` — no new
calibration surface needed, just an implementation that honors what's
already there.

`EyeConfig.lookRangeDegrees` is **not** used in this conversion — the
min/max pulse range already represents "100% of travel" for `input = ±1`.
`lookRangeDegrees` is scoped entirely to animation duration math below.

## Animation engine (`RealAnimationEngine`, replacing `PassthroughAnimationEngine`)

Two independent transitions, composed into one `EyePose` per frame (a
single animation engine owns both, rather than two separate engines
fighting over `EyeController` — this is the "unified" model):

```cpp
struct GazeTransition {
    float startX = 0.0f, startY = 0.0f;
    float targetX = 0.0f, targetY = 0.0f;
    uint32_t elapsedMs = 0;
    uint32_t durationMs = 0;
    bool active = false;
    bool blinkOnArrival = false;
};

struct EyelidTransition {
    float startUL = 1.0f, startLL = 1.0f, startUR = 1.0f, startLR = 1.0f;
    float targetUL = 1.0f, targetLL = 1.0f, targetUR = 1.0f, targetLR = 1.0f;
    uint32_t elapsedMs = 0;
    uint32_t durationMs = 0;
    bool active = false;
};
```

`update(deltaMs)`:
1. Advance `elapsedMs` on whichever transition(s) are `active`.
2. For each active transition, compute `t = ease(min(elapsedMs / durationMs, 1.0))` using that transition kind's assigned easing curve (below), lerp each field from `start` to `target` by `t`.
3. Compose the current gaze values and current eyelid values into one `EyePose` and call `eyeController_.applyPose(pose)` — once per frame, regardless of how many transitions are active.
4. When a transition's `elapsedMs >= durationMs`: clamp its fields exactly to `target`, set `active = false`. If the completed transition was the gaze transition and `blinkOnArrival` was set, immediately call `animateBlink(kDefaultBlinkDurationMs)` (150ms).

**Easing curves** — three, matching the roadmap's three named items,
assigned per animation intent (not caller-selectable this pass):

```cpp
enum class EasingType { Linear, EaseInOut, Cubic };

float ease(EasingType type, float t) {
    switch (type) {
        case EasingType::Linear:
            return t;
        case EasingType::EaseInOut:  // quadratic ease-in-out
            return t < 0.5f ? 2.0f * t * t : 1.0f - std::pow(-2.0f * t + 2.0f, 2.0f) / 2.0f;
        case EasingType::Cubic:  // cubic ease-in-out
            return t < 0.5f ? 4.0f * t * t * t : 1.0f - std::pow(-2.0f * t + 2.0f, 3.0f) / 2.0f;
    }
    return t;
}
```

Assignment:
- `animateGaze` → **Cubic** — naturalistic quick-then-settle saccade motion
- `animateBlink`/`animateWinkLeft`/`animateWinkRight`/`animateSleep`/`animateWake` → **EaseInOut** — snappy, not linear-robotic
- `animateExpression` → **Linear** (unchanged behavior otherwise — see Out of Scope)

**`GazeTarget.speed`** (degrees/second) → gaze transition duration:

```cpp
float deltaNormalized = std::max(std::abs(target.x - gazeTransition_.startX),
                                  std::abs(target.y - gazeTransition_.startY));
uint32_t durationMs = static_cast<uint32_t>(
    (deltaNormalized * calibration_.eyeConfig().lookRangeDegrees / target.speed) * 1000.0f);
```

This is the first real use of `lookRangeDegrees`, and gives `speed` a
physical meaning (degrees/second) instead of an arbitrary unitless number.

**`animateBlink`/`animateWinkLeft`/`animateWinkRight`/`animateSleep`/`animateWake`**
use their existing explicit `durationMs` parameter directly (already part
of `IAnimationEngine`'s signature since v0.1, populated from
`EyeCommand.durationMs`) — no degrees/speed math involved, since these
aren't gaze motions.

## Out of Scope (explicit, deferred to v0.3 per the already-approved roadmap)

- **`blink()`'s auto-reopen.** v0.2's `animateBlink` is a one-way animated
  transition to closed — smooth instead of instant, but still requires an
  explicit `wake()` to reopen, same as v0.1. Roadmap v0.3 item: "Animated
  blink (close + reopen)."
- **`GazeTarget.hold`.** Stored on the struct, read by nobody yet — it's a
  future signal for behavior logic (v0.3 `TrackingBehavior`/`IdleBehavior`
  deciding whether to auto-return to center), not something the animation
  engine itself should act on.
- **`setExpression()`/`animateExpression` pose blending.** Stays a no-op
  (per the v0.1 fix that made it a genuine no-op instead of silently
  recentering gaze). Defining actual per-expression target poses is v0.3
  roadmap work ("expression pose blending").
- **Caller-selectable easing.** Each intent has one fixed, sensible curve
  this pass; a per-call `EasingType` field on `GazeTarget`/`EyeCommand`
  would be premature — nothing needs it yet.

## Testing

All of the above is native-testable (no Arduino dependency in
`EyeController`, `RealAnimationEngine`, or the easing functions) via the
existing `pio test -e native` suite. New tests needed:

- `toServoOutput()`: neutral input → neutral pulse; full-scale input → pulse
  at max/min; `inverted`/`mirrored` flip the direction; `mechanicalOffset`
  shifts the result; output stays clamped to `[minPulseUs, maxPulseUs]`.
- `RealAnimationEngine`: a gaze transition reaches target only after its
  full duration, passing through intermediate (eased, not linear-lerped
  for Cubic) values in between; `blinkOnArrival` triggers a blink exactly
  once, on completion; an eyelid transition (blink/wink/sleep/wake) is
  independent of a concurrent gaze transition (both can be active and
  composed in the same frame without interfering).
- Frame pacing: `loop()`'s gate logic isn't itself unit-testable (it's in
  `main.cpp`, not a library), but the underlying `update(dt)` contract
  each module already exposes doesn't change — no new native test needed
  there beyond what v0.1 already has.
