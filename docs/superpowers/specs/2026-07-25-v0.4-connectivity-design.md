# EyeSee v0.4 — Connectivity — Design

Date: 2026-07-25

## Purpose

Give the firmware a control surface reachable over WiFi, per
`docs/ROADMAP.md`'s v0.4 milestone:

- `RestApi`: `/api/v1/*` endpoints wired to `CommandQueue`
- `WebServer`: serves `data/` control panel assets
- `WebSocketServer`: 30-60Hz state broadcast
- Web UI: joystick, blink, expressions, diagnostics

Everything here is additive to the existing pipeline
(`EyeCommand -> CommandQueue -> BehaviorEngine -> IAnimationEngine ->
EyeController -> IServoOutput`); no pipeline stage changes shape. Networking
only ever writes by pushing an `EyeCommand`, and only ever reads via
existing read-only getters (`IBehaviorEngine::state()`,
`EyeController::currentPose()`) — it never touches `IAnimationEngine` or
hardware, matching `lib/Networking/README.md`'s existing (currently
aspirational) contract.

## Scope decision: covering the full `EyeCommand` vocabulary

`docs/architecture.md`'s REST route list only documents
`status`/`look`/`blink`/`expression`/`config`, but `EyeCommand` already
supports `WinkLeft`/`WinkRight`/`Sleep`/`Wake` too — with no input source
to ever trigger them outside native tests. Rather than ship a REST surface
that can't reach part of the command vocabulary BehaviorEngine already
handles (including the `Sleep`/`Wake` state-transition behavior built in
v0.3), this pass adds `POST /api/v1/wink`, `POST /api/v1/sleep`,
`POST /api/v1/wake` alongside the previously-documented routes, and the Web
UI gains minimal wink/sleep-wake controls beyond the roadmap's literal
"joystick, blink, expressions, diagnostics" list. `GET`/`POST
/api/v1/config` stays out of scope — `docs/ROADMAP.md` explicitly assigns
config endpoints to v0.5, once `CalibrationManager` has something to
persist to.

## New dependencies

Added to `[env:esp32dev]`'s `lib_deps`:
- `ESP32Async/ESPAsyncWebServer` — async HTTP + WebSocket in one library,
  non-blocking (required: the 100Hz main loop can't tolerate blocking
  network I/O). `me-no-dev/ESPAsyncWebServer` (the original) is
  unmaintained; the `ESP32Async` org fork is the actively maintained
  successor.
- `ESP32Async/AsyncTCP` — ESPAsyncWebServer's transport dependency on ESP32.
- `bblanchon/ArduinoJson` — request/response JSON. Portable C++, no Arduino
  dependency, so it's also added to `[env:native]`'s `lib_deps`, enabling
  native-testable JSON logic (see "Protocol module" below).

`[env:esp32dev]` also gains `board_build.filesystem = littlefs` — LittleFS
replaces the unmaintained SPIFFS for serving `data/`'s static assets.
Uploading the filesystem image is a manual step
(`pio run -t uploadfs -e esp32dev`), documented in `data/README.md`.

## WiFi credentials

Real WiFi credentials must never enter version control. `main.cpp` includes
`WifiCredentials.h` (from PlatformIO's project-wide `include/` directory),
which is `.gitignore`d; `include/WifiCredentials.h.example` is committed as
the template:

```cpp
#pragma once
constexpr const char* kWifiSsid = "your-network-name";
constexpr const char* kWifiPassword = "your-network-password";
```

A developer copies the example, fills in real values, and PlatformIO's
default include path picks it up with no per-library wiring. Persisting
credentials via `PreferencesStore` (so they're runtime-configurable instead
of compile-time-fixed) is v0.5 work, once `CalibrationManager`'s
persistence pattern exists to follow.

`Configuration.h`'s existing `NetworkConfig` struct (`ssid`, `password`,
`webServerPort`) has held placeholder empty-string defaults since v0.1 with
nothing populating it. This pass gives it a real value: `main.cpp`
constructs one `NetworkConfig networkConfig{kWifiSsid, kWifiPassword,
80};`, using the two constants from `WifiCredentials.h` — so
`WifiCredentials.h` supplies only the sensitive literals, and
`NetworkConfig` stays the single struct every module reads network settings
from (matching how `EyeConfig`/`CalibrationManager` already work), rather
than two parallel, redundant sources of the same values.

## `WifiManager` (new, Arduino-only)

`lib/Networking/WifiManager.h`/`.cpp`, guarded end-to-end by `#ifdef ARDUINO`
(including its `#include <WiFi.h>`), following the exact pattern
`Pca9685ServoOutput.h`/`ArduinoRandomSource.h` already use for a
native-unignored library folder that still can't compile some of its
classes on the host:

```cpp
class WifiManager {
public:
    void begin(const char* ssid, const char* password);
    void update(uint32_t deltaMs);
    bool isConnected() const;

private:
    uint32_t msSinceLastAttempt_ = 0;
    static constexpr uint32_t kRetryIntervalMs = 5000;
};
```

`begin()` calls `WiFi.begin(ssid, password)` once (STA mode only — no AP
fallback or captive portal this pass, see Out of Scope). `update()` checks
`WiFi.status()`; if not connected and `kRetryIntervalMs` has elapsed since
the last attempt, calls `WiFi.reconnect()` and logs via `Logger`. The
firmware's eye-motion pipeline has zero dependency on WiFi state — a
disconnected or never-configured network leaves the eyes fully functional,
just unreachable remotely.

## Protocol module (new library, native-testable)

`lib/Networking` is (and stays) excluded from the `native` PlatformIO
environment (`lib_ignore` in `platformio.ini`) — ESPAsyncWebServer/AsyncTCP
are large, ESP32-only libraries, and unlike the single-header
`Adafruit_PWMServoDriver` case, the risk of their transitive includes
leaking past an `#ifdef ARDUINO` guard during PlatformIO's dependency scan
isn't worth taking for logic that doesn't need Arduino at all. Instead, all
JSON encode/decode logic is pure C++ in a new leaf library,
**`lib/Protocol`**, with zero Arduino dependency (only `ArduinoJson` +
`EyeCommand.h`/`EyeTypes.h`/`EyeState.h`), fully covered by native tests:

`lib/Protocol/EyeCommandJson.h`/`.cpp` — request parsing, one function per
route body shape:
```cpp
struct ParseResult {
    bool ok = false;
    std::string error;  // set only when ok == false
};

ParseResult parseLookCommand(const std::string& jsonBody, EyeCommand& out);
ParseResult parseBlinkCommand(const std::string& jsonBody, EyeCommand& out);
ParseResult parseWinkCommand(const std::string& jsonBody, EyeCommand& out);       // {"side": "left"|"right"}
ParseResult parseExpressionCommand(const std::string& jsonBody, EyeCommand& out); // {"expression": "Happy"}
```
`parseLookCommand` reads `x`/`y` (required floats, clamped -1..1),
`speed`/`blinkOnArrival`/`hold` (optional, default from `GazeTarget{}`'s
existing defaults), sets `out.type = CommandType::Look`. `parseBlinkCommand`
reads optional `durationMs` (default 150, matching the value already used
throughout the v0.3 test suite), sets `CommandType::Blink`.
`parseWinkCommand` requires `side` to be exactly `"left"` or `"right"`,
setting `CommandType::WinkLeft`/`WinkRight` — anything else is a parse
error. `parseExpressionCommand` maps the `expression` string to the
`Expression` enum via `expressionFromString()` (below); an unrecognized
name is a parse error, not a silent fallback to `Neutral` — a typo in a
client should be visible, not swallowed. `Sleep`/`Wake` need no body parser
— their routes construct `EyeCommand{CommandType::Sleep}`/`{Wake}` directly.

`lib/Protocol/EyeStateJson.h`/`.cpp` — response building and the
`EyeState`/`Expression` string mappings shared by parsing and responses:
```cpp
const char* eyeStateToString(EyeState state);
const char* expressionToString(Expression expression);
bool expressionFromString(const std::string& name, Expression& out);  // false = unrecognized

std::string buildStatusJson(EyeState state, const EyePose& pose, bool wifiConnected);
std::string buildBroadcastJson(EyeState state, const EyePose& pose, uint32_t uptimeMs);
std::string buildErrorJson(const std::string& message);
```
`buildStatusJson()` is the `GET /api/v1/status` body — a fuller,
occasional-request snapshot (state, pose, WiFi connectivity).
`buildBroadcastJson()` is the WebSocket payload — deliberately leaner
(state, pose, uptime only, no WiFi field) since it's sent at up to 30Hz and
every extra field costs bandwidth on every tick. Both use ArduinoJson's
`JsonDocument`/`serializeJson()`, which supports `std::string` output
directly (`ARDUINOJSON_ENABLE_STD_STRING`, on by default) — no Arduino
`String` class anywhere in this library, keeping it host-portable.

`test/test_native/test_eye_command_json.cpp` and
`test_eye_state_json.cpp` cover: valid parses for all four request shapes,
missing-required-field errors, out-of-range clamping, unrecognized
expression names, and round-tripping every `EyeState`/`Expression` value
through its string form.

## `lib/Networking` (Arduino-bound wiring)

Each class's constructor now takes the read-only references/queue it needs
— a real signature change from the current parameterless placeholders,
required to actually wire to `CommandQueue`/`BehaviorEngine`/`EyeController`
as `lib/Networking/README.md` already promises:

```cpp
class WebServer {
public:
    void begin(AsyncWebServer& server);  // registers LittleFS static handler
    void update(uint32_t deltaMs);       // no-op; request-driven, kept for
};                                        // the shared per-frame update() convention
```

```cpp
class RestApi {
public:
    RestApi(CommandQueue& commandQueue, const IBehaviorEngine& behaviorEngine,
            const EyeController& eyeController, const WifiManager& wifiManager);
    void begin(AsyncWebServer& server);
    void update(uint32_t deltaMs);  // no-op, request-driven
private:
    CommandQueue& commandQueue_;
    const IBehaviorEngine& behaviorEngine_;
    const EyeController& eyeController_;
    const WifiManager& wifiManager_;
};
```

`begin()` registers, on the shared `AsyncWebServer`:
- `GET /api/v1/status` -> 200, `buildStatusJson(behaviorEngine_.state(), eyeController_.currentPose(), wifiManager_.isConnected())`
- `POST /api/v1/look`, `/blink`, `/wink`, `/expression` -> parse via the
  matching `lib/Protocol` function; on success, push the produced
  `EyeCommand` onto `commandQueue_` and respond 202 (`{"queued": true}`);
  on parse failure, respond 400 with `buildErrorJson(result.error)`; if
  `commandQueue_.push()` returns `false` (queue full), respond 503 with
  `buildErrorJson("command queue full")` — the queue is finite
  (`CommandQueue::kCapacity = 16`) and a REST client deserves to know a
  command was dropped rather than assume it landed.
- `POST /api/v1/sleep`, `/wake` -> no body, push
  `EyeCommand{CommandType::Sleep}`/`{Wake}` directly, respond 202/503 the
  same way.

```cpp
class WebSocketServer {
public:
    WebSocketServer(const IBehaviorEngine& behaviorEngine, const EyeController& eyeController);
    void begin(AsyncWebServer& server);          // mounts an AsyncWebSocket at "/ws"
    void update(uint32_t deltaMs);               // rate-limits + broadcasts
private:
    const IBehaviorEngine& behaviorEngine_;
    const EyeController& eyeController_;
    uint32_t msSinceLastBroadcast_ = 0;
    static constexpr uint32_t kBroadcastPeriodMs = 33;  // ~30Hz, low end of the documented 30-60Hz range
};
```

`update()` accumulates `deltaMs`; once `kBroadcastPeriodMs` has elapsed,
resets the accumulator and calls `ws.textAll(buildBroadcastJson(...))`,
using millis()-since-boot for the uptime field.

## `main.cpp` wiring

```cpp
NetworkConfig networkConfig{kWifiSsid, kWifiPassword, 80};  // kWifiSsid/kWifiPassword from WifiCredentials.h
AsyncWebServer server(networkConfig.webServerPort);
WifiManager wifiManager;
WebServer webServer;
RestApi restApi(commandQueue, behaviorEngine, eyeController, wifiManager);
WebSocketServer webSocketServer(behaviorEngine, eyeController);
```
`setup()`: `wifiManager.begin(networkConfig.ssid, networkConfig.password)`,
`LittleFS.begin()`, then `webServer.begin(server)`,
`restApi.begin(server)`, `webSocketServer.begin(server)` (route
registration must precede `server.begin()`), then `server.begin()` once,
after `otaManager.begin()` and before the existing `behaviorEngine` state
setup. `loop()` gains `wifiManager.update(elapsed)` alongside the existing
`webServer.update`/`restApi.update`/`webSocketServer.update` calls (already
present as placeholder calls — only their constructors' arguments change).

## Web UI (`data/`)

A single-page vanilla HTML/CSS/JS app (no build step, no framework — this
is firmware, not a web project; keeping the toolchain to "flash and it
works" matters more than component reuse for one page):

- `data/index.html` — layout: a joystick pad, blink/wink-left/wink-right
  buttons, an expression picker (six buttons, one per `Expression` value),
  a sleep/wake toggle, and a diagnostics panel (connection state, current
  `EyeState`, current pose values, uptime).
- `data/app.js` — joystick input (pointer events on a `<canvas>` or
  absolutely-positioned `<div>`, normalized to -1..1, sent via
  `fetch('/api/v1/look', {method: 'POST', body: JSON.stringify({x, y})})`
  on drag, throttled to avoid flooding `CommandQueue`); button handlers
  posting to their respective routes; a `WebSocket` connection to `/ws`
  updating the diagnostics panel on every broadcast message; reconnect
  logic if the socket drops (`WiFi`/AP going down shouldn't require a page
  reload).
- `data/style.css` — minimal, functional styling; no external font/CDN
  dependencies (must work fully offline, served entirely from the device).

Testing note: this UI can only be exercised against real hardware (LittleFS
image flashed via `uploadfs`, ESP32 joined to WiFi) — there is no
host-side way to run ESPAsyncWebServer. It is reviewed for structural
correctness (valid HTML/JS, correct route names/payload shapes matching
`lib/Protocol`'s parse functions) as part of this milestone's task review,
but live browser verification against the physical unit is a manual step
for whoever next flashes the device, same as any other hardware-dependent
change in this project.

## Out of Scope (deferred, not v0.4)

- `GET`/`POST /api/v1/config` — v0.5, once `CalibrationManager` persists
  via `PreferencesStore`.
- WiFi credentials via `PreferencesStore`/runtime reconfiguration — v0.5,
  same reason; v0.4 credentials are compile-time via `WifiCredentials.h`.
- AP-mode fallback / captive portal for first-time WiFi setup — not in any
  milestone yet; STA-only with fixed retry is enough for a
  developer-flashed device. Worth a future roadmap line if this project
  gains non-developer users.
- Authentication/authorization on any route — this is a LAN-local hobby
  device with no accounts model anywhere in the roadmap; adding auth
  without a concrete threat model would be speculative.
- Command priority/arbitration between simultaneous REST clients —
  `CommandQueue` is already documented as strictly FIFO
  (`docs/superpowers/specs/2026-07-25-v0.3-behavior-design.md`); this pass
  doesn't change that.

## Testing

`lib/Protocol` is fully native-tested (parse success/failure paths, string
round-trips, JSON building) with zero Arduino dependency. `lib/Networking`
(`WifiManager`, `WebServer`, `RestApi`, `WebSocketServer`) stays
Arduino-only and native-ignored, verified by `pio run -e esp32dev`
compiling successfully — consistent with how `Logger`/`Storage`/`OTA`/
`MotionHardware`'s hardware-bound classes are already verified in this
project (`docs/architecture.md`'s Testing Strategy section). The Web UI is
structurally reviewed, not executed, in this milestone's task review.
