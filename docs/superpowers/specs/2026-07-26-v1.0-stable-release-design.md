# EyeSee v1.0 "Stable Release" — Design Spec

## Goal

Ship the v1.0 milestone as scoped in `docs/ROADMAP.md`: **API freeze**,
**full documentation**, **example configs**. Unlike every prior milestone
(v0.1–v0.6), this one adds no new firmware capability — it stabilizes and
documents what already exists so a new user (or a future contributor) can
build, flash, calibrate, and control a physical unit, and so the network
API can be relied upon not to change out from under existing integrations.

## Context (from project survey)

- REST (`/api/v1/*`, 9 routes), WebSocket (`/ws`, broadcast-only), and MQTT
  (`<prefix>/command` + `<prefix>/status`) protocols are all implemented
  and tested, but their documentation is scattered: route *names* are
  listed in `docs/architecture.md`, but request/response body shapes and
  status codes live only in code comments and `.cpp` implementations.
- No version string exists anywhere in the codebase — no `VERSION` file,
  no `#define`, no git tag, and no runtime version-reporting field in any
  status payload.
- The repo-root `README.md` reads as an internal module index, not a
  getting-started guide: no wiring diagram, no I2C pin assignment, no
  power-budget guidance, no calibration walkthrough, no "how to control
  the eye" section.
- `examples/` is an empty placeholder directory. `include/README.md` is
  stale (predates `MqttCredentials.h.example`, added in v0.6).
- Scattered "future work" notes already exist across several
  `lib/*/README.md` files (unregistered `CuriousBehavior`/`RandomBehavior`,
  `lookRangeDegrees` not REST-configurable, OTA has no auth, MQTT client ID
  isn't unique per device, `POST /api/v1/config` requires all fields, no
  partial patch). These are pre-existing, intentional scope boundaries, not
  new problems — v1.0's job is to document them in one place, not fix them.

## Non-goals (YAGNI)

- No new REST/MQTT/WebSocket routes or fields beyond the one version field
  below. This is a freeze, not a feature milestone.
- No implementation of any scattered "future work" item (personality
  behaviors, partial-patch config, MQTT auth, OTA auth, unique MQTT client
  IDs). These get one consolidated "Known Limitations" doc entry each,
  not code changes — changing any of them now would be undocumented scope
  creep into a milestone titled "freeze."
- No mechanical/enclosure design files (STL, CAD) — out of scope; the
  hardware doc covers electrical/wiring/BOM only, consistent with what
  this repo has ever covered (firmware, not mechanical design).
- No CI changes — the existing pipeline (native tests, esp32dev build,
  clang-format gate, informational clang-tidy) is already adequate and
  unrelated to this milestone's scope.

## What v1.0 adds

### 1. A firmware version constant, surfaced in status responses (the one intentional API change — additive only)

`include/Version.h` (new): `constexpr const char* kFirmwareVersion = "1.0.0";`
— a single source of truth, referenced by both the status-JSON builder and
(for a human reading the file) anyone checking what's flashed.

`lib/Protocol/EyeStateJson`'s `buildStatusJson()` (used by `GET
/api/v1/status` and MQTT's `<prefix>/status` publish — NOT the 30Hz
WebSocket broadcast, which deliberately stays lean, matching the existing
precedent of omitting `wifiConnected` from the broadcast payload for the
same reason) gains one new top-level field: `"firmwareVersion":
"1.0.0"`.

This is additive-only (existing consumers parsing the current fields are
unaffected) and is the mechanism that makes "API freeze" a checkable claim
rather than a promise with no evidence: from v1.0 onward, any REST/MQTT
client can confirm which frozen API version a device is actually running.

**This is a real code change** (touches `EyeStateJson.h/.cpp` and its
existing native tests, which assert the exact JSON shape) — everything
else in this milestone is documentation and example-config content.

### 2. `docs/api-reference.md` (new) — the single source of truth for the network API

Consolidates, in one place, everything currently scattered across
`docs/architecture.md`'s route-name list, `lib/Protocol/*.h` doc-comments,
and `lib/Networking/README.md`/`lib/Integrations/README.md`'s prose:

- **REST**: all 9 routes, exact request body shape (including which
  fields are required vs. optional-with-default, and each default value),
  exact success response shape and status code, every error status code
  and when it fires (400 body-validation failures, 503 queue-full,
  malformed-JSON rejected upstream by ESPAsyncWebServer before the route
  handler runs).
- **WebSocket**: the `/ws` endpoint, its 30Hz broadcast-only nature (no
  client→server messages are ever handled), and its payload shape —
  explicitly noting the two fields (`wifiConnected`, `firmwareVersion`)
  that REST's `/status` has but the broadcast omits, and why (bandwidth at
  30Hz vs. once-per-request).
- **MQTT**: both topics, the `type`-dispatch payload shape for
  `<prefix>/command` (identical field shapes to the REST bodies for the
  same command types, explicitly cross-referenced rather than
  re-documented), the `<prefix>/status` payload (identical to REST's
  `/status`), the hardcoded client ID and its known limitation (see
  Known Limitations), and the reconnect/timeout behavior already
  documented in `MqttBridge.h`'s doc-comment.
- **Versioning & stability policy** (new prose, not previously written
  down anywhere): `/api/v1/` is frozen as of v1.0 — no breaking change
  (removed field, renamed field, changed type, changed status-code
  semantics) will ever land under the `v1` path; a breaking change would
  ship as `/api/v2/` alongside the still-working `v1`. Additive,
  backward-compatible changes (a new optional field, a new route) may
  still land under `v1`. The MQTT and WebSocket protocols are covered by
  the same policy even though they have no path-based version literal —
  "frozen" for them means the same additive-only rule.

### 3. `docs/hardware.md` (new) — the wiring/BOM/power doc that doesn't exist anywhere today

- Bill of materials (from the existing root-README parts list, expanded):
  ESP32 DevKit (any board exposing the standard I2C pins), Adafruit
  PCA9685 16-channel PWM driver, 6× SG90/MG90S servos.
- I2C wiring: PCA9685 default address `0x40` (from
  `Pca9685ServoOutput.h:19`), ESP32 DevKit's default I2C pins (`SDA`=21,
  `SCL`=22 on most ESP32 DevKit boards — verify this against the actual
  `Wire.begin()` call site in the codebase before writing it down, don't
  assume from general ESP32 knowledge), PCA9685's V+ (servo power) vs. VCC
  (logic power) distinction.
- **Power budget** (the physical-build failure point the survey flagged as
  undocumented anywhere): 6 servos under load can draw well beyond a
  USB-powered ESP32 dev board's 5V pin capacity — recommend a separate 5V
  supply for the PCA9685's V+ rail, sized for the specific servo model's
  stall current × 6, with a shared ground between that supply and the
  ESP32.
- Servo channel mapping table: PCA9685 channel → name (0=LR, 1=UD, 2=TL,
  3=BL, 4=TR, 5=BR) — already consistent across three code locations per
  the survey; this doc surfaces it in one user-facing place instead of
  requiring someone to read `Configuration.h`'s comments.
- PWM frequency (50Hz) and default pulse-width range
  (1000-2000µs, neutral 1500µs, absolute allowed range 500-2500µs) from
  `Configuration.h`/`EyeConfigJson.cpp` — with a pointer to the
  calibration walkthrough (item 4) for how to actually tune these per-servo.

### 4. Root `README.md` — rewritten as a getting-started guide, not a module index

Read the current file in full before rewriting (don't discard anything
still accurate — the Architecture pipeline diagram, module table, and
Contributing/License sections are fine as-is and should be kept, just
reflowed). Add, in this order after the existing intro:

1. **Hardware** section: BOM summary + link to the new `docs/hardware.md`
   for wiring/power detail (don't duplicate the wiring table inline).
2. **Building & flashing**: the existing three `pio` commands, PLUS the
   currently-missing `pio run -t uploadfs -e esp32dev` step (required for
   the Web UI to exist at all — `data/README.md` already documents this,
   this section just needs to actually mention it) and the credential-file

3. **First boot & calibration**: a walkthrough using the real
   `POST /api/v1/config` shape from `docs/api-reference.md` — copy one
   concrete example request (e.g., calibrating the `lr` channel) so a new
   user has a working curl command to start from, not just an abstract
   shape.
4. **Controlling the eye**: one worked example each for REST (`curl`
   POSTing a `look` command), MQTT (`mosquitto_pub` to `<prefix>/command`),
   and gamepad (pairing an Xbox controller — cross-reference
   `lib/Integrations/README.md` for the button mapping rather than
   duplicating it).
5. Keep the existing Architecture/Module-table/Contributing/License
   sections, updating only what's stale (the module table already has an
   `Integrations` row per Task 11 of v0.6 — verify it's still accurate,
   don't re-add it).

### 5. `include/README.md` — fix the v0.6-era staleness

Add `MqttCredentials.h.example` alongside the existing
`WifiCredentials.h.example` documentation (same pattern: what it contains,
that the real file is gitignored, that CI provides placeholder values).

### 6. `examples/` — populate the empty placeholder directory

Replace the "reserved for future example configs" placeholder with real,
runnable content:

- `examples/calibration.json.example`: one complete, realistic
  `POST /api/v1/config`-shaped payload for a single channel (e.g. `lr`)
  with plausible pulse-width values within the documented valid range —
  a new user can literally copy this into a `curl -d @` invocation.
- `examples/rest-requests.sh`: a small shell script with one `curl`
  invocation per REST route (all 9), each preceded by a one-line comment
  naming what it does — runnable against a real device if `EYESEE_HOST`
  is set, not just a documentation snippet.
- `examples/mqtt-messages.md`: sample JSON payloads for every MQTT
  command `type`, plus a sample `<prefix>/status` publish payload, each
  with the exact `mosquitto_pub`/`mosquitto_sub` command line that would
  send/receive it.
- `examples/mosquitto-compose.yml`: a minimal single-service Docker
  Compose file running `eclipse-mosquitto` with anonymous access enabled,
  for anyone who wants to test the MQTT integration locally without
  standing up a production broker — with a one-line comment that this
  configuration (anonymous access) is for local testing only, not a
  production deployment recommendation.
- Update `examples/README.md` to describe each file above (replacing the
  placeholder text entirely).

### 7. `docs/known-limitations.md` (new) — consolidate scattered future-work notes

One doc, one entry per item, each with a one-sentence "why this is
intentional, not an oversight" note and a pointer to where it's discussed
in more depth if anywhere:
- `CuriousBehavior`/`RandomBehavior` exist but are never registered in
  `main.cpp` (`lib/Behavior/README.md`'s existing note).
- `lookRangeDegrees` has no REST-exposed way to change it
  (`lib/Configuration/README.md`'s existing note).
- OTA has no authentication (`lib/OTA/README.md`'s existing note).
- MQTT client ID is hardcoded (`"eyesee"`) — two devices on one broker
  would collide; a real deployment needs a unique ID per device (new
  observation from this milestone's survey, not previously documented
  anywhere).
- `POST /api/v1/config` requires every field per request; no partial
  patch (implicit in the current implementation, not previously called
  out as a documented limitation anywhere).
- `PubSubClient::connect()`'s residual synchronous-blocking risk on a
  slow-to-resolve broker hostname (already documented in
  `MqttBridge.h`'s doc-comment; this doc just cross-references it instead
  of duplicating it).

This doc is linked from the root README's new sections and from
`docs/api-reference.md`'s MQTT section (for the client-ID note).

### 8. `docs/architecture.md` — reconcile with the new version field and reference doc

- Update the "REST API versioning" section to state the policy from item
  2 (frozen as of v1.0, additive-only) and point to `docs/api-reference.md`
  for the full route reference, rather than continuing to be a bare route
  name list that duplicates (partially) what's now the single source of
  truth.
- Note the new `firmwareVersion` field's existence in the same section
  (one sentence), since `docs/architecture.md` is where this project's
  invariants live and "the status payload always includes a version
  field, checked by CI/integration tooling if any exists" is exactly that
  kind of invariant.

### 9. `docs/ROADMAP.md` — mark v1.0 complete

Same pattern as every prior milestone's roadmap update (see v0.6's Task 11
for the precedent): replace the `## v1.0 — Stable release` bullet list

first artifact anyone arriving at v1.0 would look for and none currently
exists.

## Testing

The only code change (item 1) needs:
- Updated native tests in `test/test_native/test_eye_state_json.cpp` (or
  wherever `buildStatusJson`'s existing shape assertions live) confirming
  `firmwareVersion` is present and equals `kFirmwareVersion`.
- Confirmation that `buildBroadcastJson`'s tests are unchanged (proving
  the field was deliberately NOT added there).
- `pio test -e native` and `pio run -e esp32dev` both still green,
  flash/RAM recorded (expect a negligible change — one new short string
  constant and one new JSON field).

Every other item (2 through 10) is documentation/example content with no
executable test, but each must be self-review-checked against the actual
current codebase before being written down (e.g., the I2C pin numbers in
item 3 must be verified against the real `Wire.begin()` call site, not
assumed) — this spec's plan will instruct each task's implementer to
verify claims against real source, matching this whole project's
established practice.
