# EyeSee v0.5 — Persistence & OTA — Design

Date: 2026-07-26

## Purpose

Make calibration survive a reboot, let the device be reflashed without a
USB cable, and give the config REST endpoint the v0.4 design spec
deliberately deferred. Per `docs/ROADMAP.md`'s v0.5 milestone:

- `CalibrationManager` <-> `PreferencesStore` persistence
- `OtaManager`: `ArduinoOTA` wiring
- Config REST endpoints (`GET`/`POST /api/v1/config`)
- `clang-tidy` in CI

## `IStorage` gains typed accessors beyond `uint16_t`

`IStorage`/`PreferencesStore` currently only support `uint16_t`
(`getUInt16`/`putUInt16`), enough for pulse widths but not for
`ServoConfig::mechanicalOffset` (`int16_t`), `inverted`/`mirrored`
(`bool`), or `EyeConfig::lookRangeDegrees` (`float`). Extend the interface
with the three missing primitive types, mirroring the ESP32 `Preferences`
API's own native support for each (`getShort`/`putShort`,
`getBool`/`putBool`, `getFloat`/`putFloat` — no serialization/encoding
needed, `Preferences` already stores these types directly):

```cpp
class IStorage {
public:
    virtual ~IStorage() = default;
    virtual bool begin(const char* namespaceName) = 0;
    virtual bool getUInt16(const char* key, uint16_t& outValue) const = 0;
    virtual bool putUInt16(const char* key, uint16_t value) = 0;
    virtual bool getInt16(const char* key, int16_t& outValue) const = 0;
    virtual bool putInt16(const char* key, int16_t value) = 0;
    virtual bool getBool(const char* key, bool& outValue) const = 0;
    virtual bool putBool(const char* key, bool value) = 0;
    virtual bool getFloat(const char* key, float& outValue) const = 0;
    virtual bool putFloat(const char* key, float value) = 0;
    virtual void end() = 0;
};
```

`PreferencesStore`'s three new method pairs each follow the exact
`getUInt16`/`putUInt16` pattern already there (`isKey()` guard on read,
`put*()`'s return value on write). A new `FakeStorage` test double
(`test/test_native/support/FakeStorage.h`) implements the full interface
in-memory (a small `std::map<std::string, Variant>` or six parallel maps —
implementer's call, either is fine, both are trivial for this key count),
enabling native tests for load/save logic without touching real flash.

## Key naming: ESP32 `Preferences`' 15-character key limit

Every persisted key must fit in 15 characters (a hard ESP32 NVS
limitation — `Preferences` silently truncates or fails past it). Six
channels (`lr`/`ud`/`tl`/`bl`/`tr`/`br`, matching `EyeChannel`'s existing
short names) times six `ServoConfig` fields, plus one top-level field:

| Field | Key pattern | Example (`lr`) |
|---|---|---|
| `minPulseUs` | `<ch>_min` | `lr_min` |
| `maxPulseUs` | `<ch>_max` | `lr_max` |
| `neutralPulseUs` | `<ch>_neu` | `lr_neu` |
| `mechanicalOffset` | `<ch>_off` | `lr_off` |
| `inverted` | `<ch>_inv` | `lr_inv` |
| `mirrored` | `<ch>_mir` | `lr_mir` |
| `EyeConfig::lookRangeDegrees` | `lookRange` | (once, no channel prefix) |

`ServoConfig::channel` (the PCA9685 channel index) is never persisted —
it's a fixed, compile-time property of which `EyeChannel` a `ServoConfig`
belongs to (`makeDefaultEyeConfig()` already assigns it), not a
user-calibratable value.

## `CalibrationManager` gains explicit load/save, not constructor-injected storage

`CalibrationManager`'s existing constructors
(`CalibrationManager()`, `explicit CalibrationManager(const EyeConfig&)`)
stay exactly as they are — no `IStorage&` parameter added. Existing native
tests construct a `CalibrationManager` with no storage at all and must keep
working unchanged. Instead, two new methods:

```cpp
/** Loads every persisted key that exists, leaving any missing key at its current
 * (default-constructed) value -- so a first boot with an empty namespace is
 * indistinguishable from "nothing persisted yet," not an error. Returns true if
 * at least one key was found and loaded. */
bool loadFromStorage(IStorage& storage);

/** Writes every field of the current EyeConfig to storage. */
void saveToStorage(IStorage& storage) const;
```

`setServoConfig()` itself stays storage-agnostic (pure in-memory mutation,
as today) — it does not call `saveToStorage()` internally. The composition
root (`main.cpp`) calls `calibration.loadFromStorage(preferencesStore)`
once at startup, after `preferencesStore.begin("eyesee")`; the new
`POST /api/v1/config` REST handler (below) calls `setServoConfig()` then
`saveToStorage()` explicitly, in that order, so a config write is
save-on-write rather than requiring a separate "commit" step. This keeps
`CalibrationManager` exactly as testable as it is today (no `IStorage`
dependency baked into construction) while still making persistence
automatic from a REST client's point of view.

## `OtaManager` wraps `ArduinoOTA`

```cpp
class OtaManager {
public:
    /** Starts the ArduinoOTA listener. Call once from setup(), any time after
     * WifiManager::begin() -- ArduinoOTA doesn't require an active connection
     * yet at call time, only once a client actually attempts an update. */
    void begin();
    /** Services pending OTA requests. Cheap no-op when no update is in progress
     * or WiFi is disconnected. */
    void update(uint32_t deltaMs);
};
```

`begin()` calls `ArduinoOTA.setHostname("eyesee")` then `ArduinoOTA.begin()`
(no password this pass — see Out of Scope). `update()` calls
`ArduinoOTA.handle()` unconditionally every frame; `ArduinoOTA.handle()`
is itself a fast no-op when no client is mid-upload, so this doesn't need
its own rate-limiting the way `WebSocketServer`'s broadcast does. No
native test (Arduino-only, `lib/OTA` already in `native`'s `lib_ignore`) —
verified only by `pio run -e esp32dev` succeeding, same as every other
hardware-bound class in this project.

## Config REST endpoints

`GET /api/v1/config` returns the full, current `EyeConfig` — all six
channels plus `lookRangeDegrees` — as one JSON diagnostic snapshot (not
paginated or channel-scoped; six channels' worth of config is small).
`POST /api/v1/config` updates exactly one channel per request, matching
`CalibrationManager::setServoConfig(EyeChannel, const ServoConfig&)`'s
existing shape — a calibration UI adjusts one servo at a time, and a
single-channel body keeps the request small and the failure mode scoped
(a bad `offset` value for one channel doesn't risk garbling the other
five in the same request).

Request/response shapes (built by two new `lib/Protocol` functions,
following the same split as v0.4's `EyeCommandJson`/`EyeStateJson` — pure,
native-testable JSON logic in `lib/Protocol`, Arduino-bound route wiring in
`lib/Networking`):

```cpp
// lib/Protocol/EyeConfigJson.h
struct ConfigParseResult {
    bool ok = false;
    std::string error;
    EyeChannel channel = EyeChannel::Lr;  // valid only when ok == true
    ServoConfig servoConfig;              // valid only when ok == true
};

/** {"channel": "lr", "minPulseUs": 1000, "maxPulseUs": 2000, "neutralPulseUs": 1500,
 *  "mechanicalOffset": 0, "inverted": false, "mirrored": false} -- every field required
 *  (a partial per-field patch isn't worth the complexity this pass; a calibration UI
 *  always has the current values in hand already, from a prior GET, to round-trip). */
ConfigParseResult parseConfigUpdate(JsonVariantConst body);

/** GET /api/v1/config response body: full EyeConfig snapshot. */
std::string buildConfigJson(const EyeConfig& config);
```

`channel` accepts the same lowercase two-letter names as the persistence
key prefixes (`"lr"`, `"ud"`, `"tl"`, `"bl"`, `"tr"`, `"br"`) — one more
small string<->enum mapping, `channelFromString`/`channelToString`,
alongside `EyeChannel` (natural home: `lib/Protocol/EyeConfigJson.h`, since
`EyeChannel` itself lives in `lib/Configuration`, a leaf module that
shouldn't gain a JSON dependency).

`buildConfigJson(const EyeConfig&)`'s output is one object keyed by
`channelToString()`'s six names, each holding that channel's full
`ServoConfig` (the same six fields `parseConfigUpdate` reads), plus a
top-level `lookRangeDegrees`:

```json
{
  "lr": {"minPulseUs": 1000, "maxPulseUs": 2000, "neutralPulseUs": 1500,
         "mechanicalOffset": 0, "inverted": false, "mirrored": false},
  "ud": { ... }, "tl": { ... }, "bl": { ... }, "tr": { ... }, "br": { ... },
  "lookRangeDegrees": 30.0
}
```

`RestApi::begin()` gains two more routes:
- `GET /api/v1/config` → 200, `buildConfigJson(calibrationManager_.eyeConfig())`.
- `POST /api/v1/config` → parse via `parseConfigUpdate`; on failure, 400 +
  `buildErrorJson(result.error)`; on success,
  `calibrationManager_.setServoConfig(result.channel, result.servoConfig)`
  then `calibrationManager_.saveToStorage(preferencesStore_)`, respond 200
  with `buildConfigJson(calibrationManager_.eyeConfig())` (the full,
  updated config — lets a client confirm the write without a second GET).
  `RestApi`'s constructor gains two more references:
  `CalibrationManager&` (needs to be mutable — `setServoConfig()` isn't
  `const` — unlike every other v0.4 dependency, which were all
  `const&` read-only) and `IStorage&` (so `RestApi` can call
  `saveToStorage()` without owning a `PreferencesStore` itself).

This is the one place `RestApi` holds a non-const reference to something
it mutates — a deliberate, narrow exception to v0.4's
"Networking only ever writes by pushing an `EyeCommand`" framing.
Calibration isn't part of the `EyeCommand`/`CommandQueue`/`BehaviorEngine`
pipeline at all (it's static per-servo tuning, not a live gaze/expression
action), so routing a config write through `CommandQueue` would misuse a
queue designed for time-ordered eye-motion commands to carry a completely
different kind of request. `docs/architecture.md`'s invariants are about
the motion pipeline (`EyeController`/`MotionHardware`/`Behavior`/the v0.4
`Networking` read/write rule); calibration writes were never part of that
pipeline's scope, so this isn't a violation of any of the four existing
invariants — it's a fifth, narrower rule worth stating explicitly:
**`RestApi`'s config route is the one place allowed to call
`CalibrationManager::setServoConfig()` directly** (see Out of Scope for
why this isn't generalized further).

## `clang-tidy` in CI

Add a new CI step, after the existing formatting check:

```yaml
      - name: Generate compile_commands.json
        run: pio run -t compiledb -e esp32dev

      - name: Install clang-tidy
        run: sudo apt-get install -y clang-tidy

      - name: Run clang-tidy
        run: clang-tidy -p . $(find lib src -name '*.cpp')
```

`pio run -t compiledb -e esp32dev` (not `native`) because it covers the
larger file set — every `lib/` folder including the Arduino-bound ones
(`Logger`, `MotionHardware`, `Storage`, `OTA`, `Networking`), whereas
`native`'s compile database would only cover the native-testable subset.
A new `.clang-tidy` config file (repo root) scopes checks to this
project's own conventions and excludes vendored dependencies:

```yaml
Checks: >
  bugprone-*,
  performance-*,
  readability-*,
  -readability-magic-numbers,
  -readability-identifier-length
HeaderFilterRegex: '(lib|src)/.*'
```

`readability-magic-numbers` is excluded because this codebase's calibration
constants (pulse widths, degrees, hex I2C addresses) are meaningful literal
values, not magic numbers needing named constants everywhere — the existing
code already names the ones that matter (`kMinPulseUs` etc. in `Configuration.h`)
and follows its own judgment elsewhere. `readability-identifier-length`
is excluded because this codebase's existing short names (`lr`, `ud`, `tl`,
etc., matching the `EyeChannel` enum and hardware silkscreen labels) are
deliberate domain vocabulary, not a real problem the linter should flag.
`HeaderFilterRegex` restricts findings to this project's own `lib/`/`src/`
files, so `clang-tidy` doesn't report on vendored ESPAsyncWebServer/
ArduinoJson/Adafruit library headers pulled in via `#include`. CI treats
`clang-tidy` output as informational this pass (no `--warnings-as-errors`,
no CI failure on findings) — turning it into a hard gate is worth doing
once a first full run's baseline is known and triaged, not blindly on
day one against a codebase that's never been linted before.

## Out of Scope (deferred, not v0.5)

- WiFi credentials via `PreferencesStore` (persisted/runtime-configurable
  instead of compile-time `WifiCredentials.h`) — the v0.4 spec already
  deferred this to v0.5, but it's deferred again here: v0.5's actual
  roadmap bullets are calibration persistence + OTA + config endpoints +
  clang-tidy, and none of them require credential persistence. Revisit
  once there's a concrete driver (e.g. a captive-portal first-run flow).
- `ArduinoOTA` password/authentication — matches v0.4's REST/WebSocket
  auth deferral (LAN-local hobby device, no accounts model anywhere in the
  roadmap); revisit together if a real threat model ever emerges for this
  project.
- Generalizing "one `RestApi` route may mutate a non-`EyeCommand` piece of
  state" beyond calibration — `EyeCommand`/`CommandQueue` stays the only
  path for anything that affects live eye motion; calibration is a static
  tuning value with no timing/ordering concerns a queue would need to
  arbitrate, which is precisely why it's the one carve-out.
- Partial per-field `PATCH`-style config updates — `POST /api/v1/config`
  requires the full six-field `ServoConfig` body this pass; a client
  always has the current values from a prior `GET` to round-trip, so a
  partial-patch endpoint isn't solving a real problem yet.
- `clang-tidy` as a hard CI gate — informational only this pass (see above).

## Testing

`IStorage`'s three new type pairs and `CalibrationManager::loadFromStorage`/
`saveToStorage` are fully native-tested via a new `FakeStorage` double
(`test/test_native/support/FakeStorage.h`), following the exact pattern
`FakeAnimationEngine`/`FakeRandomSource`/`FakeServoOutput` already
established. `lib/Protocol/EyeConfigJson`'s parse/build functions are
native-tested the same way Task 2/3's `EyeStateJson`/`EyeCommandJson` were
in v0.4. `PreferencesStore`'s three new method pairs and `OtaManager` stay
Arduino-only, verified only by `pio run -e esp32dev` compiling
successfully, matching every other hardware-bound class in this project.
